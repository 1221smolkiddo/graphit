# P1: durable memory and provider-neutral handoff

**History is immutable. Memory is derived. Context is disposable.**

P0 remains the persistence foundation. Its original migration is unchanged. P1 adds explicit durable memory, evidence-bearing relationships and a structured handoff. It does not index code, run models, extract memory automatically, summarize conversations or budget tokens.

## Packages and files

The dependency order is `core → storage → memory → CLI`. `@graphit/memory` owns memory schemas/types (`src/domain.ts`), temporal replay (`src/replay.ts`), disposable projection persistence (`src/projection.ts`), handoff assembly (`src/handoff.ts`) and the public `MemoryService` API (`src/index.ts`). Its three test suites cover memory behavior, migration preservation and process/CLI integration.

`@graphit/core` adds `source-schemas.ts` and optional session metadata. Memory schemas are registered by importing `@graphit/memory`, avoiding a core/storage dependency on the memory package. Construct `MemoryService(store)` before writing to a memory-bearing project. This installs the memory validator/projector on that connection; attempting memory writes without it fails closed. The CLI always installs it.

`@graphit/storage` adds a synchronous, project-scoped transaction API and projection hooks. Sequence allocation, provenance validation, source event insertion and all derived writes are inside the same `BEGIN IMMEDIATE` transaction. A failed projection or second step of supersession rolls back the entire operation.

## Migration 002

`packages/storage/migrations/002_memory.sql` adds `memory_entities`, `memory_relations`, and five nullable session metadata columns. Neither memory table is canonical. They deliberately do not depend on other disposable projection rows through foreign keys; replay enforces project/session/entity relationships.

P0's `events.event_type` has a fixed CHECK constraint. Migration 002 widens that one constraint using SQLite's [documented schema-only procedure](https://www.sqlite.org/lang_altertable.html#otheralter), avoiding copying, deleting or replacing source rows. The runner checks the expected schema text, refreshes the SQLite schema version, checks integrity inside the transaction and always disables schema editing afterward. The original event table, root page, rowids, indices and update/delete/replacement protections remain in place. Tests upgrade a populated P0 database and verify the old event rows, migration checksum and checkpoint hash are unchanged. Older P0 binaries reject the newer schema; this is a forward-only upgrade.

## Durable entity contract

`MemoryEntity` contains:

```ts
{
  id: string;                         // deterministic SHA-256 entity identity
  project_id: string;
  entity_type: 'goal' | 'task' | 'decision' | 'constraint' | 'blocker'
    | 'question' | 'action' | 'result' | 'artifact';
  content: string;
  status: 'active' | 'in_progress' | 'completed' | 'resolved' | 'cancelled' | 'superseded';
  created_at: string;
  source_event_ids: string[];         // nonempty; original evidence + lifecycle event IDs
  created_by_session_id: string;
  valid_from_sequence: number;        // creation sequence, inclusive
  valid_to_sequence: number | null;   // supersession/cancellation sequence, exclusive
  superseded_by: string | null;
  metadata: Record<string, JsonValue>;
}
```

Provenance may reference any earlier immutable event in the same project, including memory lifecycle events. Missing, future and cross-project references fail closed. The entity's own creation event and later transition events are retained as provenance as well. No source payload is overwritten.

Promotion identity is SHA-256 over a versioned domain marker, project ID, entity type, exact content, sorted unique source IDs and metadata. Repeating the same promotion returns the same entity without appending another event, even from another session. Content and provenance are never inferred. Distinct evidence or content creates a distinct identity.

`active → in_progress → completed` applies to goals, tasks and actions (direct active-to-completed is allowed). Blockers/questions use `active → resolved`. Any active/in-progress entity can be cancelled. Completed/resolved/cancelled states cannot be reopened in P1. `memory resolve` uses completed for goals/tasks/actions and resolved for blockers/questions; it rejects decisions, constraints, results and artifacts.

Completion/resolution remains valid historical knowledge, so `valid_to_sequence` stays null. Cancellation/supersession closes the validity interval. Status at an earlier point is reconstructed from source events with `getMemoryState(projectId, throughSequence)`. This returns the inclusive event prefix, not a mutable saved snapshot.

## Supersession and relationships

Superseding Decision A, “Use Neo4j”, creates or selects active Decision B, “Use SQLite”, then appends `memory.entity.superseded`. A retains its original content and creation metadata, gains `status: superseded`, `valid_to_sequence`, and `superseded_by: B.id`. B stays active. The derived relation is `B SUPERSEDES A`, the inverse of `A SUPERSEDED_BY B`. Both identities and their source events remain recoverable.

A replacement must be a different, active entity of the same type. An already superseded/cancelled entity cannot be superseded again. Creation of a replacement and supersession are one atomic operation. No update/delete is issued against `events`.

Relationships support `PART_OF`, `DEPENDS_ON`, `BLOCKS`, `RESOLVES`, `PRODUCED`, `VERIFIED_BY`, `SUPERSEDES`, `RELATED_TO`. Each has its own deterministic ID, project, endpoints, type, source event IDs, creation session/time, validity interval and metadata. Endpoints and evidence must exist in the same project. A `SUPERSEDES` link also enforces the supersession transition. Other relationship labels record a link; for example, `RESOLVES` does not silently change a blocker's status—resolve it explicitly.

## Event schemas

P0's four event types remain supported. `session.started` accepts optional `provider`, `agent_name`, `model_name`, `external_session_id`, `client_name`. All accept arbitrary nonempty strings; there is no provider allowlist. Missing fields remain absent during replay, preserving P0 checkpoint hashes. Starting a new session makes it current without deleting the previous session. P0 `resume` keeps its existing JSON output and checkpoint semantics.

| New event | Required payload (optional fields marked `?`) |
| --- | --- |
| `conversation.user_message` | `content`, `metadata?` |
| `conversation.assistant_message` | `content`, `metadata?` |
| `tool.call` | `call_id`, `tool_name`, JSON `input` |
| `tool.result` | `call_id`, JSON `output`, `is_error?` |
| `command.executed` | `command_id`, `command`, `cwd?` |
| `command.result` | `command_id`, `exit_code`, `stdout`, `stderr` |
| `file.changed` | `path`, `change_type` (`added/modified/deleted`), `before_hash?`, `after_hash?`, `diff?` |
| `test.result` | `status` (`passed/failed/skipped`), `summary`, `command?`, `metadata?` |
| `memory.entity.created` | `entity_id`, `entity_type`, `content`, `source_event_ids`, `metadata` |
| `memory.entity.status_changed` | `entity_id`, `status`, `source_event_ids` |
| `memory.entity.superseded` | `entity_id`, `replacement_id`, `source_event_ids` |
| `memory.entity.linked` | `relation_id`, `from_entity_id`, `to_entity_id`, `relation_type`, `source_event_ids`, `metadata` |

All schemas reject unknown fields. Raw text is retained exactly. Source events require the current project session. Raw messages/tools/commands/files/tests do not create memory automatically. P1 validates tool/command correlation IDs as strings but does not implement a tool execution engine or correlate those external IDs automatically.

## API and example

```ts
import { EventStore } from '@graphit/storage';
import { MemoryService } from '@graphit/memory';

const store = new EventStore('/existing/project/.graphit/graphit.db');
const memory = new MemoryService(store);
try {
  const projectId = store.findProject('/existing/project')!.project!.id;
  const session = store.startSession(projectId, {
    provider: 'any-provider', agent_name: 'any-agent', client_name: 'terminal',
  });
  const source = store.appendEvent({
    project_id: projectId, session_id: session.id,
    event_type: 'conversation.user_message',
    payload: { content: 'Use SQLite for local persistence' },
  });
  memory.promoteMemory(projectId, {
    sourceEventIds: [source.id], entityType: 'decision',
    content: 'Use SQLite for local persistence',
  });
  memory.rebuildMemoryProjection(projectId); // Only this project's derived rows.
  console.log(JSON.stringify(memory.generateHandoff(projectId), null, 2));
} finally {
  store.close();
}
```

Other methods: `listMemory(projectId, { type?, status? })`, `getMemoryState(projectId, throughSequence?)`, `changeStatus`, `resolveMemory`, `supersedeMemory`, `linkMemory`. Source ingestion is explicit through `EventStore.appendEvent`; no provider connection is needed.

Run `node examples/handoff-demo.mjs` after building for a disposable local demonstration. [examples/handoff.json](../examples/handoff.json) is a complete generated packet with real hashes and evidence references; it is not a prose summary or a mock provider format.

## CLI

```sh
graphit session start --provider any-provider --agent any-agent --model any-model
graphit memory add --type decision --content "Use Neo4j" --source-event <event-id>
graphit memory list --type decision --status active
graphit memory supersede <old-id> --content "Use SQLite" --source-event <new-evidence-id>
graphit memory supersede <old-id> --with <existing-replacement-id>
graphit memory resolve <task-or-blocker-id>
graphit handoff --json
```

Repeat `--source-event` for multiple evidence IDs. Superseding with new content requires new explicit provenance; selecting an existing replacement can use its recorded provenance. Resolve optionally accepts `--source-event`, otherwise it retains the entity's existing evidence and adds the status event itself. Both `graphit handoff` and `graphit handoff --json` output JSON. Other commands support `--json` and readable text. From the checkout, use `npm run graphit -- <command>`; in Windows PowerShell, `npm.cmd exec -- graphit --help` avoids PowerShell interpreting the help flag.

## Handoff semantics

The canonical JSON packet has `schema_version: "1"`, project/current session, goals, active/completed tasks, active decisions/constraints, unresolved blockers/questions, actions, latest results, artifacts, durable history, relationships, exact evidence and the source sequence range.

Superseded decisions are excluded from `decisions` and preserved in `history`. Completed tasks are separate from active tasks. `recent_results` contains the latest 20 current results in reverse creation order; older results remain in `history`. History also preserves superseded/cancelled memory and resolved questions/blockers. Evidence is the exact immutable source events referenced by durable items, their lifecycle and author sessions, plus project/current-session identity. Unpromoted conversation is not dumped into the packet, but remains in the event store.

`generated_at` is the timestamp of the last event in the source range, not the wall clock, so an unchanged event prefix generates byte-stable JSON. There is no LLM or generated prose. `generateHandoff()` validates history, restores missing/stale projections, and reads those projections under one transaction. It appends no source events. Deleting every memory projection cannot destroy handoff capability.

## Verification and limitations

Run `npm test`, `npm run typecheck`, `npm run lint`. Tests cover every entity and relation type, invalid schemas/provenance, temporal status and supersession, source preservation, project isolation, exact projection reconstruction, WAL/concurrency, upgrade/rollback and the CLI. A separate-process integration test has an anthropic/claude-code session create a goal, decision, task and result and exit; an openai/codex session starts later and obtains the same provider-neutral state with exact evidence. It then deletes memory projections and verifies identical regenerated handoff JSON.

P1 deliberately uses synchronous full replay and rewrites derived memory rows inside each write. Handoff generation rebuilds projections and takes a write lock. This prioritizes verification and recovery over large-history throughput. Handoff includes durable history with no size/token limit. There is one current session per project; starting another makes old sessions inactive. It does not contact providers or implicitly end sessions on process exit. Raw source ingestion and memory promotion are manual APIs, not automatic capture. No cloud sync, vector search, code graph, ranking, token budget, summarization, MCP or editor integration exists.
